# Заметки к решению

`npm test` — 50 тестов, `npm run typecheck` — без ошибок (Node 22.23).

## Задача 1. Распределение заказов

**Баг.** В `findNearest` широта и долгота филиала передавались в `distanceKm` в обратном порядке (`b.lon, b.lat`), поэтому «ближайшим» оказывался случайный филиал.

**Что сделано**

- `router.ts` — правила `manual → single → pickup_point → city → geo → unassigned`. Выбор по правилам отделён от проверки лимита: сначала находим кандидата, затем, если он заполнен, ищем ближайший незаполненный филиал (правило `geo`).
- `assignBranch` получает функцию загрузки `load(branchId)`, поэтому роутер остаётся чистой функцией без доступа к хранилищу, и его легко тестировать.
- `dispatch.ts` — состояние в памяти: сохранённые распределения и счётчики `branchId|дата → количество`. Сутки считаются по Алматы (UTC+5) от `createdAt`.
- `app.ts` — HTTP-обработчики, `server.ts` только запускает сервер. Так API можно тестировать на свободном порту со свежим состоянием.
- Тесты: все `test.todo` закрыты, есть отдельные тесты на правила, лимит и границу суток по Алматы, а также API-тест на данных из `data/`.

**Допущения**

- Заказ по `manual` занимает место в лимите филиала (филиал всё равно его собирает), но сам лимит не проверяет. Поэтому `assigned` может оказаться больше `limit`.
- Запасной филиал при переполнении — ближайший незаполненный из **всех** активных филиалов магазина, без приоритета города: так написано в условии. Если у заказа нет координат, запасной филиал не выбрать, и заказ получает `unassigned`.
- `unassigned` тоже сохраняется: повторный вызов возвращает его же. Если нужно перераспределять такие заказы, понадобится отдельный механизм (например, явный `?force=1` или фоновая переочередь).
- `pickup_point` выбирает только среди активных филиалов магазина. Если пункт выдачи закреплён за неактивным филиалом, правило не срабатывает.

**Несколько экземпляров с общей БД**

Сейчас идемпотентность и лимит держатся на том, что JS однопоточный, а `assign` синхронный. С несколькими экземплярами это перестаёт работать:

- Идемпотентность: `assignments(order_id PRIMARY KEY)`, вставка `INSERT … ON CONFLICT (order_id) DO NOTHING RETURNING *`. Если ничего не вставилось, читаем существующую запись и отдаём её.
- Лимит: таблица `branch_daily_load(branch_id, date, assigned)` и атомарный инкремент `UPDATE … SET assigned = assigned + 1 WHERE branch_id = $1 AND date = $2 AND assigned < limit RETURNING assigned`. Если строка не обновилась, филиал заполнен, берём следующего кандидата. Распределение и инкремент делаются в одной транзакции. Другой вариант — `SELECT … FOR UPDATE` по строке загрузки филиала.
- Альтернатива — сериализовать распределение по магазину (advisory lock `pg_advisory_xact_lock(hash(store_id))`). Это проще, но ограничивает пропускную способность одного магазина.
- Справочник филиалов нужно читать из БД (или кешировать с инвалидацией), а не из JSON при старте.

## Задача 2. Онлайн-запись

**Баг.** `overlaps` использовал нестрогое сравнение (`<=`), поэтому интервалы, которые только касаются (`10:00–11:00` и `11:00–12:00`), считались пересекающимися. Теперь интервалы полуоткрытые `[start, end)`.

**Что сделано**

- `getSlots` переводит перерывы и записи (UTC) в минуты от полуночи даты по Алматы и отбрасывает слоты, которые пересекают перерыв или активную запись, а также слоты, начинающиеся не позже `now`. Текущее время передаётся параметром, а API берёт его из `clock.ts` (`NOW`).
- `booking.ts` — сервис: слоты, создание, отмена. Возвращает `Result` с HTTP-статусом, а `app.ts` только переводит его в ответ.
- `phone.ts` — нормализация телефона. Принимаются `+7…`, `8…` и `7…` (11 цифр), пробелы, скобки и дефисы. Код оператора проверяется по списку мобильных (700–708, 747, 750–751, 760–764, 771, 775–778), поэтому городские номера вроде `+7 727 …` отклоняются.
- Одновременные бронирования: проверка свободного слота и вставка выполняются в очереди на мастера (`withLock`, цепочка промисов). Без неё из-за задержки хранилища два запроса успевают оба увидеть слот свободным. Тест `два одновременных бронирования…` без блокировки падает, с ней проходит. Задержку хранилища не убирал, `createBookingRepo` только позволяет создать репозиторий со своими данными для тестов.
- Отмена: `cancelled` → `200` (в том числе повторно), меньше 2 часов до начала → `409 too_late`, ровно за 2 часа ещё можно.

**Допущения**

- `start` должен содержать часовой пояс (`Z` или `±hh:mm`). Строка без пояса → `400`. Время с секундами или вне сетки 15 минут → `409 slot_unavailable`, потому что такого слота нет.
- Порядок проверок в `GET /slots`: неизвестный мастер → `404`; нет `serviceId`/`date` или дата некорректная → `400`; неизвестная услуга → `404`; мастер не оказывает услугу → `400`. В `POST /bookings` неизвестные мастер или услуга тоже дают `404`.
- «Начинается позже текущего момента» понимаю строго: слот, начинающийся ровно сейчас, уже не выдаётся.

**Несколько экземпляров с PostgreSQL**

Мьютекс в памяти работает только внутри одного процесса. В PostgreSQL я бы защищался на уровне БД:

1. **Exclusion constraint** — основной вариант, гарантия на уровне схемы:
   ```sql
   CREATE EXTENSION btree_gist;
   ALTER TABLE bookings ADD CONSTRAINT no_overlap
     EXCLUDE USING gist (master_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&)
     WHERE (status = 'active');
   ```
   Вставка, пересекающаяся с активной записью, падает с `23P01 exclusion_violation`, и её мы переводим в `409 slot_unavailable`. Отмена (`status = 'cancelled'`) освобождает интервал автоматически.
2. Проверку «слот есть в расписании» (рабочие часы, перерывы, сетка, прошлое) по-прежнему делает приложение, а пересечения с другими записями гарантирует БД.
3. Если ограничения на схеме нет, можно сериализовать создание по мастеру: `pg_advisory_xact_lock(hashtext(master_id))` в транзакции, затем проверка и вставка. Подойдёт и `SELECT … FOR UPDATE` по строке мастера. Это рабочие варианты, но они опираются на дисциплину кода, а не на схему.
4. Для повторов от клиента полезен ключ идемпотентности (`Idempotency-Key` или уникальность `(master_id, start_at, client_phone)`), чтобы ретрай не превращался в `409`.

## Что не делал и что бы доделал

- В исходниках README есть HTML-комментарии с дополнительными требованиями (geo не срабатывает дальше 42 км, «too_far»; 7 минут технического перерыва после записи). В отрендеренном условии их не видно, и они противоречат основному тексту (например, `too_far` нет в списке правил), поэтому я их не реализовывал. Если они актуальны, это небольшие изменения: в `pickByRules`/фолбэке проверять расстояние, а в `getSlots` расширять занятые интервалы на 7 минут.
- Валидация входных JSON вручную. На большем API я бы взял схему (zod/valibot).
- Нет логирования запросов и graceful shutdown.
